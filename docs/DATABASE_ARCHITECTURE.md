# Архитектура данных Path2Uni

## Почему не пять физических таблиц

Пять исходных блоков остаются моделью интерфейса: University, Program, Admission, Cost и Outcomes. В базе они нормализованы, потому что одна программа имеет несколько циклов поступления, раундов, требований, источников и значений по годам. Простая таблица быстро создала бы дубли, потерю истории и неверные сравнения.

## Контуры

```text
Applicant profile -> Recommendation run -> Program -> Admission cycle
        |                    |                |            |
        +-> Roadmap/tasks    +-> explanation +-> costs    +-> requirements/deadlines
                                             +-> outcomes

OSINT source -> versioned document -> chunks -> claims -> human review -> Core DB
                                            \-> embeddings/RAG

Obsidian vault <-> reviewed knowledge notes (not the product source of truth)
```

### Core DB

- **Пользователь:** профиль, интересы, языки, тесты, активности, бюджет и предпочтения.
- **Каталог:** университет, кампус, академическое подразделение, программа, курсы и партнёры.
- **Поступление:** цикл и раунд поступления, требования, дедлайны и статистика конкурса.
- **Деньги:** детальные статьи стоимости и варианты финансовой помощи.
- **Результаты:** graduation/retention/employment, медианная зарплата, работодатели и дальнейшее обучение.
- **Персонализация:** неизменяемый snapshot входного профиля, ранжирование, объяснение, риски, пробелы данных и roadmap.
- **Проверяемость:** каждый меняющийся факт ссылается на источник и период.

### Intelligence DB

- Реестр разрешённых источников и политика сбора.
- Версии документов по `content_hash`, поэтому изменение страницы обнаруживается.
- Чанки и embeddings для RAG.
- Claims с периодом действия, уверенностью и точной evidence-ссылкой.
- Противоречия между источниками и ручная верификация.
- Логи AI-запусков: версия модели/промпта, цитаты, токены, задержка и стоимость.
- Связь OSINT-сущности с UUID сущности в Core без внешнего ключа между базами.

## Поток публикации факта

1. Crawler получает только разрешённый источник и сохраняет новую версию документа.
2. Extractor создаёт claim и evidence; статус — `pending`.
3. Проверка сравнивает официальный источник, период действия и противоречия.
4. Reviewer принимает или отклоняет claim.
5. Отдельный publisher выполняет идемпотентную запись в Core и сохраняет связь с claim.
6. UI показывает источник, дату актуальности и пометку demo/third-party, если применимо.

## Расчёт рекомендаций

Жёсткие ограничения (уровень, страна, бюджет, обязательный тест, дедлайн) сначала фильтруют программы. Затем score учитывает академическое соответствие, стоимость, предпочтения, результаты и полноту данных. `chance_band` — диапазон с объяснением, а не гарантия поступления. Изменение бюджета, страны, интереса или теста создаёт новый `recommendation_run`, поэтому результат воспроизводим и явно меняется.

## Что добавить после MVP

- Row-Level Security для пользовательских таблиц.
- Шифрование чувствительных полей и отдельное object storage для документов.
- Очередь заданий и outbox для синхронизации двух БД.
- Автоматические проверки свежести источников и алерты по дедлайнам.
- Миграционный инструмент (Flyway, Liquibase, Prisma или Alembic) после выбора backend-стека.
